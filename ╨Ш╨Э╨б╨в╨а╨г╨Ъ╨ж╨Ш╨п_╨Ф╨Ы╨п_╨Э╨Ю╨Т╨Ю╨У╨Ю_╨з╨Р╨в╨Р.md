# Инструкция для нового чата — сайт dan4ik37

Актуальное состояние проекта на сентябрь 2026. Старая версия этого файла
описывала монолитный `index.html` на ~4400 строк — с тех пор сайт разбит на
модули, добавлена регистрация, четыре роли и панель управления ими,
восстановление пароля, мобильная адаптация админ-функций. Если начинаешь
новый чат — прочти это целиком перед тем, как что-то менять.

## 1. Что это за проект

Сайт стримера dan4ik37: `dan4ik37.github.io`, хостинг Vercel, бэкенд —
Supabase (Postgres + Auth + Realtime + Storage). Разделы: видео с YouTube,
Twitch-плеер, чат в реальном времени, донат-цель, лидерборд донатеров,
опросы, расписание стримов, кастомные эмодзи, кликер-игра, саундборд,
пасхалка и т.д.

Репозиторий: `git clone https://github.com/dan4ik37/dan4ik37.github.io.git`
(доступен для чтения из песочницы — `github.com`/`codeload.github.com`
разрешены в сетевых настройках).

Полная таблица размеров — в конце файла.

### Почему НЕ `type="module"`

Резать хотели через ES-модули (`export`/`import`) — красивее и современнее.
Отказались из-за реальной ловушки: `<script type="module">` **всегда**
выполняется отложенно (как `defer`), уже после парсинга всего HTML. А в
разметке сотни `onclick="playSound(...)"` и подобных — они читают функции
как простые глобальные переменные в момент клика. Если бы часть кода была
модулем, а часть — обычным скриптом, порядок выполнения на старте мог бы
не совпасть с тем, что есть сейчас, и что-то бы тихо ломалось на живом
сайте при первой загрузке.

Поэтому все файлы — **обычные classic-скрипты** (`<script src="...">` без
`type="module"`). Это значит:
- **Порядок `<script>`-тегов в `index.html` жёстко важен.** Файл, что-то
  использующий (например `youtube.js` использует `esc()` из `utils.js`),
  обязан идти в разметке ПОСЛЕ файла, который это определяет.
- Никаких `export`/`import` — просто `function foo(){}` / `let x = ...`
  на верхнем уровне файла, и оно становится доступно во всех скриптах
  дальше по документу (так же, как было в старом монолите).
- `core/config.js` и `core/state.js` **обязаны** идти первыми двумя —
  от них зависит буквально всё остальное.

Актуальный порядок подключения (не менять без причины):
```
config.js → state.js → tabs-nav.js → schedule.js → utils.js → youtube.js
→ modal.js → chat.js → twitch.js → soundboard.js → easter-egg.js
→ clicker-game.js → donation-goal.js → settings-panel.js
→ role-management.js → donation-alerts.js → google-translate.js
→ init.js → router.js → hotkeys.js
```
(плюс `custom-emoji.js`, `polls.js`, `reactions.js`, `push-pwa.js`,
`global-auth.js`, `leaderboard.js`, `performance-mode.js` — идут между
`chat.js` и `google-translate.js`, порядок между собой не критичен, они
друг от друга не зависят). `role-management.js` обязан идти после
`chat.js` (использует `sbClient`, `currentRole`, `currentUser`) и после
`utils.js` (использует `esc()`).

### Ловушка, которая реально была найдена при разбивке

Логика **опросов** была физически раскидана по **трём несвязанным местам**
в старом монолите: массив `POLLS`+`pollIdx` лежал в одном месте, функции
голосования (`votePoll`/`renderPoll`) — в другом, а админ-редактор опросов
(`openPollAdmin` и т.д.) — вообще рядом с кодом глобальной авторизации,
без всякой смысловой связи. Всё это теперь собрано в один `polls.js`.
Если в будущем будешь резать похожий монолит — не верь секционным
комментариям `// ═══ НАЗВАНИЕ ═══`, они не гарантируют, что весь код на
эту тему лежит рядом.

### Как проверялась разбивка (и все последующие правки)

На каждое изменение:
1. `node --check файл.js` — синтаксис не сломан
2. Проверка баланса HTML-тегов во всём `index.html` (простой Python-скрипт
   на `html.parser.HTMLParser`)
3. Сверка, что каждая функция, вызываемая из `onclick="..."` в разметке,
   реально существует хотя бы в одном из файлов `js/`
4. **Самое важное — и раньше пропущенное:** каждый файл в `js/` должен
   иметь ровно один `<script src="...">` в `index.html`, без дублей и
   без "потерянных" файлов. Пункт 3 сам по себе НЕ ловит эту ошибку —
   функция может существовать в файле, который просто не подключён.
   Именно так один чат случайно удалил тег `global-auth.js` при чистке
   дублей (заодно зацепив ещё 6 тегов — reactions/polls/push-pwa/
   leaderboard/custom-emoji/performance-mode), и вход на сайт молча
   перестал работать на несколько сообщений, пока не заметили. Команда:
   ```python
   import re, subprocess
   with open('index.html', encoding='utf-8') as f: html = f.read()
   tags = re.findall(r'<script src="(js/[^"]+)"', html)
   all_files = set(subprocess.run(['find','js','-name','*.js'],
                    capture_output=True, text=True).stdout.split())
   print('Дубли:', [t for t in set(tags) if tags.count(t)>1] or 'нет')
   print('Без тега:', all_files - set(tags) or 'нет')
   print('Тег в никуда:', set(tags) - all_files or 'нет')
   ```

Держи эту привычку и дальше — все четыре проверки быстрые и ловят
практически все поломки от ручной правки classic-скриптов.

## 3. Система ролей

Четыре роли + гость. Роль хранится в `profiles.role` (Supabase, обычное
текстовое поле, без CHECK-ограничения на список значений):

| Роль | Значок | Может |
|---|---|---|
| `admin` | 👑 | Всё: банить, удалять сообщения, редактор опросов/расписания/цели/эмодзи, назначение ролей, настройки сайта, live-алерты о донате |
| `moderator` | 🛡 | Банить + удалять сообщения. Админ-панелей не видит |
| `helper` | 🧹 | **Только** удалять сообщения. Не банит, админ-панелей не видит |
| `user` | 👤 | Обычный зарегистрированный аккаунт. В чате — как гость, но с постоянным ником |
| гость (без аккаунта) | — | Пишет в чат под случайным `Гость1234`, без сохранения между устройствами |

### Назначение ролей — через UI

«⚙️ Настройки сайта» → раздел «👥 Роли» → поиск зарегистрированного
зрителя по нику → выпадающий список → «Сохранить» (с подтверждением
перед записью). Логика в `role-management.js`, поиск идёт по `nick` в
`profiles` — по email искать нельзя, `auth.users` не читается с
фронтенда, это правильно и безопасно так и должно быть.

Гостю роль выдать нельзя в принципе — у него нет строки в `profiles`,
не с кого спрашивать. Сначала обязана быть регистрация (раздел 4).

Требует SQL-политику **"Админ редактирует любой профиль"** из
`registration.sql` (пункт 2b) — без неё RLS пускает только к
собственной строке, и назначение чужой роли будет молча падать.

## 4. Вход, регистрация и «забыл пароль»

### Два разных способа получить ник в чате

Фиксирую явно, чтобы не путалось:

1. **«Войти как гость»** (кнопка внутри самого чата, `enterAsGuest()` в
   `chat.js`) — генерит случайный `Гость1234`, кладёт в `localStorage`.
   Без email, без пароля, без аккаунта. Стёр куки — потерял личность.
2. **«Войти» / «Регистрация»** (кнопка в шапке сайта, модалка
   `globalAuthModal`, логика в `global-auth.js`) — настоящий аккаунт
   Supabase Auth. Ник постоянный, работает с любого устройства, и только
   такому аккаунту можно выдать роль `helper`/`moderator`/`admin`.

### Регистрация — поток

`doGlobalRegister()` в `global-auth.js`:
1. Валидация полей (ник ≤24 символа, пароль ≥6 символов, пароли совпадают)
2. `sbClient.auth.signUp({email, password})`
3. Дальше два варианта, в зависимости от настройки Supabase
   (Authentication → Providers → Email → **Confirm email**):
   - **Выключено** (сессия приходит сразу): дописываем в `profiles.nick`
     то, что человек ввёл в форме, — по умолчанию туда попадает часть
     email до `@` (это делает триггер в БД, см. `registration.sql`)
   - **Включено** (нужно подтвердить почту): сессии ещё нет, показываем
     «проверь почту», ник временно кладём в `localStorage`
     (`d37_pending_nick`) и досохраняем в профиль при первом реальном
     входе после подтверждения (это в `onAuthStateChange` в `chat.js`)

Профиль (`profiles` row с `role='user'`) создаётся **автоматически**
триггером в БД на `auth.users` — не зависит от фронтенда и от того,
подтверждена почта или нет (`SECURITY DEFINER`, не клиентский INSERT).

### Забыл пароль — поток

1. Ссылка «Забыли пароль?» под полем пароля на вкладке входа →
   `doForgotPassword()` → `sbClient.auth.resetPasswordForEmail(email, {redirectTo: location.origin + location.pathname})`
2. Письмо ведёт обратно на сайт со специальным токеном восстановления в
   URL. Supabase SDK сам парсит этот токен (`detectSessionInUrl` включён
   по умолчанию) и шлёт событие `PASSWORD_RECOVERY`
3. На это событие в `initSupabase()` (в `chat.js`) повешен слушатель
   `sbClient.auth.onAuthStateChange(...)`, который открывает модалку
   сразу на третьей вкладке — «новый пароль» (`switchAuthTab('reset')`)
4. `doPasswordReset()` — валидация (пароль ≥6 символов, совпадение),
   `sbClient.auth.updateUser({password})`, дальше обновляет профиль как
   при обычном входе

Модалка входа теперь на **три вкладки**: Вход / Регистрация / Новый
пароль (`gauthLoginFields` / `gauthRegisterFields` / `gauthResetFields`
внутри одного `#gauthLogin`, переключаются `switchAuthTab(mode)`).

⚠️ **Нужно проверить в самом Supabase** (не SQL, дашборд-настройка):
Authentication → URL Configuration → домен сайта должен быть в списке
`Redirect URLs`, иначе письмо отправится, но ссылка в нём не сработает.
Это единственная часть флоу, которую я не могу проверить сам — нет
доступа к дашборду Supabase, только `git clone` репозитория для чтения.

## 5. Что нужно выполнить в Supabase — `registration.sql`

Файл лежит рядом с этой инструкцией. Выполнить **целиком** в Supabase →
SQL Editor. Все команды через `DROP ... IF EXISTS` / `CREATE OR REPLACE`,
повторный запуск всего файла безопасен, если что-то добавилось. Делает:

1. Триггер на `auth.users`, который сам создаёт строку в `profiles`
   (`role='user'`) при регистрации — см. раздел 4
2. RLS-политики на `profiles`:
   - читать может любой
   - редактировать свою строку может её владелец
   - **(2b)** редактировать ЛЮБУЮ строку может тот, у кого уже
     `role='admin'` — нужно для панели «👥 Роли» (раздел 3)
3. Триггер-защита: менять `role` может только тот, у кого уже
   `role='admin'` — иначе через тот же UPDATE-запрос, которым фронтенд
   обновляет ник, можно было бы прописать себе роль самостоятельно.
   Работает независимо от того, какая из политик пункта 2 пропустила
   запрос — проверяет роль ДЕЙСТВУЮЩЕГО пользователя, а не источник
   разрешения.

## 6. Мобильная адаптация админ-функций

Отдельно проходились по панели администратора и модерации в чате именно
на телефоне — были реальные, а не гипотетические проблемы:

- Кнопки «✏️ Редактировать» (расписание/цель/опросы) были вклеены прямо
  внутрь `<h2>` с дисплейным шрифтом `clamp(2.2rem,5vw,3.8rem)` — на
  узком экране ехало криво. Вынесены в отдельную строку-обёртку
  (`.sec-title-row`), на мобильном кнопка переносится под заголовок
- Кнопки удаления/бана/реакции на сообщениях в чате были 22×22px —
  пальцем не попасть. На тач-устройствах (`@media(pointer:coarse)`)
  увеличены до 30×30px с пересчитанными отступами
- Модалки «⚙️ Настройки сайта» и «🗳️ Редактор опросов» на экранах
  ≤480px — уменьшены внешние отступы, `max-height:92vh`, кнопка закрытия
  увеличена до 38×38px на тач-устройствах
- Строка дня в расписании переносится на две строки на совсем узких
  экранах вместо сжатия в кашу; чекбоксы увеличены до 20×20px
- Мелкие кнопки в списках (редактировать/удалить опрос, удалить эмодзи)
  — минимум 32×32px на тач-устройствах

Всё это через `@media(pointer:coarse)` и `@media(max-width:480px)` — на
десктопе с мышкой ничего не поменялось, увеличение размеров срабатывает
только там, где реально тыкают пальцем.

## 7. Визуальная полировка

Прошлись по дизайну на предмет типовых «генеричных» штампов — не
переделывали с нуля (сайт большой, вся вёрстка завязана на конкретные
классы/id, которые дёргает JS, полный редизайн — неоправданный риск),
только точечные, безопасные для функциональности правки:

- **Убраны ALL-CAPS «eyebrow»-подписи** над каждым заголовком секции
  («Статистика», «Смотреть» и т.д. — 13 штук). Они дублировали то, что
  и так видно по самому заголовку (Bebas Neue, крупно), и это ровно тот
  паттерн, который выдаёт шаблонную генерацию. Вместо текстовой подписи
  — короткая акцентная чёрточка слева от заголовка (`.sec-title::before`,
  градиент accent→accent2), не текст, просто визуальный якорь
- **Смягчена scroll-reveal анимация** — раньше каждая из 17 секций при
  скролле одинаково выезжала на 30px снизу с fade; это тоже типовой
  «разбросанный» паттерн. Сдвиг уменьшен до 10px — герой (аватарка,
  аврора, glitch-эффект на HIGH) и так уже несёт всё «яркое» движение
  сайта, остальные секции не должны с ним спорить
- **Добавлена поддержка `prefers-reduced-motion`** — системная настройка
  «уменьшить анимацию» (для людей с вестибулярной чувствительностью).
  Раньше учитывался только внутренний performance-режим (`body.low`,
  про слабые устройства) — это другое, ОС-настройку никто не спрашивал.
  Теперь спрашивают: `@media (prefers-reduced-motion: reduce)` глушит
  анимации независимо от performance-режима
- **Видимое кольцо фокуса** (`:focus-visible`) для клавиатурной
  навигации — раньше было только у нескольких полей ввода через смену
  цвета рамки, для остального сайта индикатора фокуса не было вообще

**Герой-секцию (`.hero`) не трогали** — она уже была на хорошем уровне:
вращающееся кольцо аватарки, аврора-орбы, glitch-пульс и typing-эффект
на HIGH-производительности, staggered-появление элементов. Это и есть
то единственное место, где сайт «тратит смелость» — раздел
про дизайн-гайд (`/mnt/skills/public/frontend-design/SKILL.md`) прямо
советует не размазывать яркие эффекты по всему сайту, а держать один
запоминающийся момент.

## 8. Что заблокировано и почему

- **Живой статус Twitch** (и пуш-уведомление о старте стрима, который от
  него зависит) — нужны `client_id`/`client_secret` с dev.twitch.tv,
  их никто не давал. Заведёшь приложение там — пришли ключи, дело на
  один заход.
- **Цель доната из нативного виджета DonationAlerts** — осознанно не
  делалось, не баг. У DA нет REST-эндпоинта, отдающего текущее состояние
  цели, поэтому цель редактируется вручную через «⚙️ Настройки сайта».

`router.js` раньше понимал только плоские маршруты (`#/chat`, `#/donate`)
— хэш с `/` внутри (типа `#/forum/42`) тихо откатывался на главную,
потому что `PAGES['forum/42']` не существует. Теперь:
- `currentRoute()` — как и раньше, возвращает только имя раздела
  (`"forum"` для хэша `#/forum/42`) — старые вызовы в `hotkeys.js` и
  `chat.js` не сломаны, у них ничего менять не пришлось
- `currentRouteParam()` — новая функция, отдаёт всё, что после первого
  `/` (для `#/forum/42` это `"42"`). Сам роутер это никак не использует,
  просто передаёт странице, которая уже сама решает, что с этим делать

Ей будет пользоваться форум (id темы) и, возможно, бот (deep-link на
конкретное сообщение).

### 8.1 Форум

**Зачем через `#/forum/id`, а не отдельным HTML-файлом:** весь сайт
сейчас — один документ, все переходы происходят без перезагрузки (см.
раздел про роутер выше) — чат, вход, perf-режим не сбрасываются. Форум
как отдельная страница `forum.html` эту модель сломает. Правильно —
ещё один `id` в `PAGES` (`forum: ['forum']`) и секция
`<section id="forum">` в разметке, как у всех остальных разделов.

**Таблицы (Supabase):**
```sql
create table public.forum_threads (
  id bigint generated always as identity primary key,
  author_id uuid references auth.users(id) not null,
  title text not null,
  pinned boolean default false,
  locked boolean default false,
  created_at timestamptz default now()
);
create table public.forum_posts (
  id bigint generated always as identity primary key,
  thread_id bigint references public.forum_threads(id) on delete cascade not null,
  author_id uuid references auth.users(id) not null,
  body text not null,
  created_at timestamptz default now(),
  edited_at timestamptz
);
```
RLS: читать могут все, создавать темы/посты — только зарегистрированные
(`auth.uid() is not null`; гостям, в отличие от чата, форум лучше не
открывать — иначе спам без всякой возможности разобраться, кто писал).
Редактировать/удалять — автор своего поста, плюс admin/moderator/helper
как в чате (та же модель прав, что уже есть).

**Фронтенд:** новый `features/forum.js`. Внутри — свой маленький
роутинг на основе `currentRouteParam()`: нет параметра → список тем
(`#/forum`), есть → открыть тему (`#/forum/42`). Переиспользовать то,
что уже есть: `esc()` для экранирования, паттерн модерации
del/ban-кнопок из чата, `trapModalFocus`/`releaseModalFocus` для формы
создания темы как модалки.

**С чего начать:** сначала просто список тем + создание темы + просмотр
с ответами, без пагинации (сайт и так небольшой, лимит `.limit(50)`
вместо реальной пагинации хватит на первое время). Модерацию и
закрепление тем — вторым заходом.

### 8.2 Интеграция с Discord-ботом

Конкретной архитектуры пока не было — сам бот и то, что он должен уметь,
не описаны. Вот три реалистичных варианта на выбор, от простого к
полному:

**A. Бот как ещё один участник чата (проще всего).**
Таблица `messages` в Supabase уже общая для всех посетителей сайта —
`chat.js` рендерит любую строку в ней независимо от источника. Бот
просто пишет туда напрямую через Supabase service-role key (у него по
определению доступ мимо RLS) при получении сообщения в Discord. На
сайте это просто появится как обычное сообщение в чате. Из правок на
сайте — по желанию добавить колонку `source text default 'web'` в
`messages` и мелкий бейдж в `addMsg()` в `chat.js`, если нужно визуально
отличать "из Discord".

**B. Односторонний мост через вебхук на сайте.**
Новый `api/bot-webhook.js` (serverless-функция Vercel) — бот шлёт туда
POST с секретным токеном в заголовке, функция валидирует и делает
INSERT в `messages`. Чуть больше контроля (валидация, рейт-лимит на
уровне сайта), чем вариант A, но требует держать секрет синхронизированным
между ботом и Vercel-переменными окружения.

**C. Двусторонняя синхронизация (сайт → Discord тоже).**
Чтобы сообщения с сайта тоже улетали в Discord — Supabase Database
Webhook (или Edge Function) на `INSERT` в `messages`, который дёргает
Discord-вебхук URL. Делать это **не** через фронтенд (`chat.js`) —
тогда webhook URL Discord утёк бы в клиентский код и любой мог бы им
воспользоваться. Только на стороне БД/сервера.

**Рекомендация:** начинать с **A** — меньше всего кода, сразу рабочий
результат, дальше по необходимости достраивать до **C**, если понадобится
дублирование сайт→Discord. Модерация (бан/роль) синхронизировать между
ботом и сайтом — отдельный вопрос, зависит от того, должен ли бан в
Discord банить и на сайте (скорее всего нет, это разные системы
идентичности — Discord ID и Supabase `profiles.id` никак не связаны без
отдельной таблицы-связки).

### 8.3 Другие разумные доработки (идеи, не заявки)

- **Настраиваемые уведомления** — сейчас push один на всех о старте
