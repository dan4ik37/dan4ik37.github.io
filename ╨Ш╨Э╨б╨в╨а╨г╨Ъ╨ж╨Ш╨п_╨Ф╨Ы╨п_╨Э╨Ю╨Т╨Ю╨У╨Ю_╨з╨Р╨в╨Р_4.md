# dan4ik37 — ХВОСТ: доработки из dan4ik37-improvements.zip

**Статус: ничего из этого файла ещё НЕ реализовано.** Прошлая сессия успела
только изучить код и составить план — ни одна строчка сайта не менялась.
Проверено командой `find . -newer <последний файл прошлой сессии>` прямо
перед тем, как писать эту инструкцию — список изменений пуст.

Человек прислал `dan4ik37-improvements.zip` (в этом архиве, файлы
`incoming/README.md` и `incoming/index.html` — это ЖИВАЯ демонстрация с 7
рабочими примерами, не патч, вставлять как есть нельзя, из неё нужно
переносить идеи и код в реальный сайт вручную) и попросил: «главное не
накосячь» + в конце сказать, какие SQL-миграции нужны.

## Что решено делать (моё решение из прошлой сессии, можно пересмотреть)

Ранжировано по README самой демки на «без бэкенда / чуть больше работы /
нужен бэкенд». Решение: сделать ВСЁ, кроме ачивок — их сознательно отложить,
а не делать наспех и криво. Если человек не против, ачивки — отдельным
заходом позже.

1. **Длительность и статус просмотра на карточках видео** — без бэкенда
2. **Плавающая кнопка доната с кольцом прогресса** — без бэкенда, но должна
   брать НАСТОЯЩИЕ цифры цели, не выдуманные
3. **Калькулятор стоимости VIP** — без бэкенда, чистый фронтенд поверх уже
   существующей покупки VIP
4. **Командная палитра Ctrl+K** — чуть больше работы, но без бэкенда
5. **Конфетti/тост при достижении 100% цели** — чуть больше работы, без
   бэкенда
6. **Реферальная система** — НУЖЕН бэкенд/SQL. Именно тут будут новые
   SQL-миграции, которые человек просил перечислить в конце.
7. **Ачивки** — ПРОПУСТИТЬ в этом заходе (см. обоснование ниже)

### Почему ачивки пропущены
Слишком много независимых точек интеграции для одного захода без риска
что-то не заметить и сломать: нужны хуки в отправку сообщения чата, в
голосование опроса, в создание темы форума, в первый донат, плюс таблица
прогресса и логика стриков (streak) захода. Это отдельная, самостоятельная
задача размером с любую из уже сделанных в этом проекте (VIP-баланс,
профиль/мини-профиль и т.п.) — лучше делать её отдельным заходом вдумчиво,
чем впихивать седьмым пунктом в общий список и рисковать недотестировать.

## Что уже проверено и можно брать как факт (не перепроверять с нуля)

Всё ниже — результат чтения реального кода в этой сессии, не предположения.

**Видео/YouTube (`js/features/youtube.js`):**
- Запрос к `/videos` сейчас берёт `part=statistics` (строка с `ytFetch`,
  ищи `youtube/v3/videos?part=statistics`) — **нет `contentDetails`**,
  поэтому длительности (`duration`, формат ISO 8601 вроде `PT18M24S`) в
  ответе пока нет. Нужно поменять на `part=statistics,contentDetails` и
  распарсить `v.contentDetails.duration` при заполнении `dm[id]`.
- Карточки строит `function renderVids(vids)` (примерно с строки 163).
- **Про «прогресс просмотра»:** в демке это выдуманный процент. Реального
  API воспроизведения (YouTube iframe API с `postMessage`/`onStateChange`)
  на сайте сейчас нет и подключать его — отдельная большая задача. Честная
  альтернатива без вранья: бинарная отметка «уже открывал это видео»
  (по клику на карточку — `openVid` — писать id в `localStorage` в Set, и
  рисовать при рендере не процент, а простую галочку/полоску «просмотрено»).
  Не выдавать это за процент реального просмотра.

**Плавающая кнопка доната:**
- На сайте уже ЕСТЬ два фиксированных элемента в правом/нижнем углу:
  `#perfToggle` — справа, по вертикали ПО ЦЕНТРУ экрана (`position:fixed`,
  правый край);
  `#scrollTop` — низ-право, `bottom:1.5rem;right:1rem` на десктопе,
  `bottom:calc(58px + env(safe-area-inset-bottom) + .7rem);right:.7rem` на
  мобильном (там ещё нижняя таб-бар панель на мобильном, из-за неё этот
  отступ).
- Демка ставила свою плавающую кнопку донат тоже в `right:1.1rem;bottom:1.3rem`
  — это АНЕТ, столкнётся с `#scrollTop`. Решение: ставить новую FAB-кнопку
  **слева снизу** (`left:1.5rem;bottom:1.5rem`) на десктопе, и **скрывать её
  на мобильном** (`@media(max-width:768px){display:none}`) — на мобильном и
  так есть «Донат» в нижней таб-баре, дублировать незачем, плюс там банально
  тесно (нижняя таб-бар + сама FAB + safe-area).
- Единая точка входа для «сколько сейчас собрано» — функция
  `initGoalBar(currentVal)` в `js/features/donation-goal.js` (самое начало
  файла, около строки 8). Через неё проходит ЛЮБОЕ обновление суммы на
  сайте — значит, синхронизацию FAB-кольца и проверку «дошли до 100%»
  (для конфетти, см. ниже) правильно повесить ВНУТРИ или сразу после вызова
  этой функции, одним местом на весь сайт, а не размазывать по местам,
  где что-то стучится в `/api/donations`.
- **Важная деталь, которую нашли:** `let goalCurrentVal = 0;` объявлена в
  начале файла с комментарием «считается само», но по факту НИГДЕ не
  присваивается заново — то есть сейчас это мёртвая переменная, всегда 0.
  Настоящее «сколько сейчас» живёт только как параметр `currentVal` внутри
  вызова `initGoalBar` и как текст в `#goalCurrent`. Раз новым функциям
  (FAB, конфетти) нужно читать «текущее собрано» НЕ только в момент вызова
  `initGoalBar`, а в любой момент — стоит наконец начать реально
  присваивать `goalCurrentVal = cur;` в первой строке `initGoalBar`. Это
  безопасное изменение — от текущего «всегда 0» ничего не зависит.

**VIP-калькулятор:**
- Сейчас в `index.html` (ищи `id="vipPromoTiers"`, чуть ниже) стоит
  `<select id="vipBuyMonths">` с вариантами 1/2/3/6/12 месяцев, и кнопка
  `<button onclick="openVipBuyGuide()">`.
- `openVipBuyGuide()` (в js/features/*.js) читает
  `document.getElementById('vipBuyMonths').value` НАПРЯМУЮ — то есть если
  заменить `<select>` на ряд кнопок «1/3/6/12 месяцев» в духе демки, **id
  `vipBuyMonths` нужно СОХРАНИТЬ** (например, спрятанным `<input type="hidden"
  id="vipBuyMonths" value="3">`, который ряд кнопок обновляет по клику) —
  тогда `openVipBuyGuide()` вообще не нужно трогать, ноль риска что-то
  сломать в уже работающей покупке VIP.
- Цена за месяц — константа `VIP_RUB_PER_MONTH` (используется в
  `js/features/profile.js`, строки ~486-495) = 100. Калькулятор должен
  вычислять `months * VIP_RUB_PER_MONTH`, а не хардкодить 100 повторно.

**Командная палитра Ctrl+K:**
- В `js/ui/hotkeys.js` есть строка вида
  `if(e.ctrlKey||e.metaKey||e.altKey) return;` — то есть Ctrl/Cmd/Alt
  СЕЙЧАС ничего не перехватывают, конфликтов с Ctrl+K нет, можно вешать
  свободно.
- Список реальных маршрутов для палитры — атрибуты `data-route="..."` в
  `index.html` (те же самые, что использует бегущая строка героя и меню
  «Ещё»): `home`(видео), `about`, `donate`, `chat`, `forum`, `lfg`,
  `poll`, `soundboard`, `clicker`, `ads`, `profile`. Переход — обычный
  `location.hash = '#/' + route`, роутер (`js/ui/router.js`) сам подхватит.

**Конфетти/тост при 100%:**
- Триггер вешать в `initGoalBar` (см. выше) — сравнивать проценты, а не
  вызывать при каждом рендере. Обязательно требуется анти-спам:
  хранить в `localStorage` ключ вида «за какую именно цель уже
  отпраздновали» (например, хэш/строка из `goalTitleText + goalMaxVal +
  goalSinceISO`), и салютовать только когда текущий процент впервые дошёл
  до 100% для ЭТОЙ конкретной комбинации — иначе будет салютовать на КАЖДОЙ
  загрузке страницы, если цель уже давно выполнена, или не салютовать
  вообще для новой цели, если использовать один и тот же ключ для всех.
  Canvas для эффекта — по аналогии с уже существующими canvas-эффектами в
  `js/features/fx.js` (там уже есть похожий паттерн для кликов-искр на
  главной), туда же логично добавить и функцию конфетти.

**Реферальная система (бэкенд/SQL):**
- Ник (`profiles.nick`) уже **гарантированно уникален** — это проверено
  триггером `enforce_unique_nick()` (файл `vip-secure.sql`, строка ~59,
  переустановлен позже в `server-hardening.sql` с более ранним именем
  триггера `a1_...`, чтобы сработать раньше). Значит, реферальный код
  можно **не городить отдельной колонкой** — использовать сам `nick` как
  код приглашения (`?ref=<nick>` в ссылке), ровно как предлагает README
  демки.
- Профили создаются триггером `handle_new_user()` (файл `registration.sql`)
  на INSERT в `auth.users` — он уже читает `new.email` для ника по
  умолчанию. Нужно ТУДА ЖЕ добавить чтение
  `new.raw_user_meta_data->>'ref'` и по нему (регистронезависимо) искать
  `profiles.id where lower(nick)=lower(ref)`, записывая в новую колонку
  `profiles.referred_by uuid references profiles(id)`. Это атомарно и
  безопасно — колонка проставляется в момент создания профиля, без гонок.
- Фронтенд должен: (1) на любой загрузке страницы поймать `?ref=` из URL и
  сохранить в `localStorage` (переживает переходы до момента регистрации);
  (2) при вызове `sbClient.auth.signUp(...)` в `js/features/global-auth.js`
  передать `options: { data: { ref: localStorage.getItem('d37_ref') } }`
  (только если значение реально есть) — именно это попадёт в
  `raw_user_meta_data`, которую читает триггер выше.
- **Статистика «Друзей»** на странице профиля УЖЕ ЗАНЯТА — это настоящая
  система друзей/заявок (таблица `friendships`, панель «Заявки в друзья»,
  `friendsList` и т.п. из более ранней сессии). Для рефералов нужен
  **отдельный слот статистики**, не путать с друзьями — README демки сам
  предупреждал об этом риске, и это подтвердилось чтением реального кода.
- Засчитывать реферала предлагается только если приглашённый профиль
  реально активен (не мусорная регистрация) — прокси-критерий: есть хотя
  бы одна запись в `messages` с его `user_id`. Функции для этого ещё не
  написаны (это и есть SQL, который нужно будет добавить и потом перечислить
  человеку): что-то вроде `referral_count(uid)` (считает активных
  приглашённых) и `top_referrers(limit)` (публичный топ для лидерборда).
- **Осознанно решено НЕ делать в этом заходе:** автоматическую выдачу наград
  по лесенке из демки (цветной ник на 7 дней за 3 реферала, роль «Посол
  сообщества» за 5 и т.п.) — это трогает уже сложную систему VIP-уровней и
  цветов ника, на автомате легко налажать. Вместо этого — просто показывать
  админу/стримеру честные цифры (сколько у кого активных рефералов), а
  награды выдавать вручную через уже существующую админку ролей. Если
  захочется автоматизировать — отдельным, отдельно протестированным заходом.

## Как продолжать в новом чате

1. Загрузить `incoming/index.html` и `incoming/README.md` из этого архива
   (или попросить у человека `dan4ik37-improvements.zip` заново) — это
   демка с рабочим кодом всех 7 идей, откуда переносить конкретную
   разметку/CSS/JS (не копировать файл целиком, только нужные куски).
2. Загрузить `dan4ik37-site.zip` — текущий реальный сайт, ещё БЕЗ этих
   доработок.
3. Реализовывать по одному пункту, каждый раз проверяя как в прошлых
   сессиях этого проекта: `node --check` на все тронутые `.js`, полный
   прогон по всем маршрутам в High/Low без ошибок консоли (Playwright,
   `regress.py`-подобный скрипт уже отработан в истории чата), для
   SQL — реальный PostgreSQL (в этой песочнице `apt-get install postgresql`
   уже ставился и работал, шаблон mock-схемы Supabase — в истории чата).
4. Реферальную систему — тестировать так же строго, как VIP-баланс и
   бэкфилл донатов в этом же проекте: реальный Postgres для триггера и
   функций, Node-моки для фронтенда `signUp`.
5. В конце — **обязательно перечислить человеку, какой именно новый SQL-файл
   выполнить** (человек явно просил не забыть это сказать). Скорее всего
   это будет отдельный `referrals.sql` (не трогать `server-hardening.sql` —
   он и так уже большой, лучше новый небольшой файл специально под
   рефералов, раз это логически отдельная фича).
